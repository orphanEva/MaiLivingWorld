# 连续对话验收

`evaluations/companion_scenarios.json` 是完全合成的多轮情境，不包含真实QQ、聊天或账号资料。它用于检查相处连续性、明确更正、模糊表达不擅自结案、少重复追问、听众边界和真实工具结果，不用于证明意识或打“活人分”。

## 先导出情境

### v0.21 建议效果的真实链路

在测试副本开启建议和统一心智active。准备一条已经入库、属于本人或公开可说的原始资料，按以下流程验证：

1. 让AI调用 `living_world_advice sources` 再 `prepare`；草稿返回后查看list，尚未发送应为draft。失败发送、加前后缀或引用草稿都不应算成功送达。
2. 原样独立发送成功后应为active，但结果仍未知。主人不反馈、只说“听起来不错”或“以后试试”，都不能更新为有效。
3. 主人引用建议中唯一具体片段，明确说亲自试了并说明效果。确认两阶段复核后才保存本人反馈；同一句若可能对应两条建议应保留未知，不猜最近一条。
4. 先报有用再明确更正没用，尤其在前一批模型未返回时发送更正；最终不得由较旧结果覆盖新反馈。再次聊相关情况时，她应承认旧方法不适用并调整建议，不把一次自述当客观普遍结论。
5. 用完整本人指令停止或忘记；重启、重放旧反馈、迟到回执不能复活结果。群聊/别人自称主人、换消息后旧草稿、来源撤回、共读后文都不能借这个工具绕过原有边界。

原有静态情境仍可单独导出：

v0.21 的建议效果和话题承接需要实际发送回执，按本文新增步骤和 [伴侣说明](COMPANION.md) 验收；静态情境不代表真实宿主链路已通过。

v0.19 的习惯和任务回告另需按 [伴侣说明](COMPANION.md) 验收真实Hook和服务链：长期技术详细默认被本轮简短要求覆盖；一次不满不变成长期偏好；只有真实任务、成功发出的承诺才开始跟进；真实结果成功送达才算回告。原有8组静态多轮情境不替代这些服务与发送回执检查。可使用小型可控任务，并分别模拟失败发送、换会话、停用来源和免打扰。

在插件源码或解压后的插件目录执行：

```sh
python scripts/evaluate_companion.py --export
```

默认运行和导出都不调用模型，不读取插件运行数据库、环境凭据或私人配置。可按情境顺序在隔离测试实例中人工交互；不要将合成事件注入日常使用的长期记忆。

## 检查已有测试回复

准备UTF-8 JSON：顶层是情境ID，值是按轮次排列的回复字符串数组。ID与轮数按导出文件填写，不用真实聊天代替合成情境。

```sh
python scripts/evaluate_companion.py --responses synthetic-responses.json
```

结果只含情境/轮次ID、规则结果、耗时和人审清单，不回显回复正文或异常详情。保管原始回复文件仍由操作者负责。关键词规则可能误判同义表达、否定和引用，不能代替人工复查；离线输入的检查通过，也不代表任何实际模型已经通过验收。

## 接入你部署的实际回复链

提供可导入的Python函数，显式选择 `--runner 模块名:函数名`：

```sh
python scripts/evaluate_companion.py --runner local_evaluation:reply
```

这会执行指定适配器，可产生真实模型费用及适配器自身的操作。使用你自己编写、审查过的适配器和独立测试实例。脚本不会自动连接QQ、读取API Key或替你选择供应商。

函数接收一个请求字典，可以同步或异步返回回复字符串，或恰好 `{"reply": "回复"}`。请求包含 `case_id`、`turn_index`、`session_id`、`sender`、`audience`、`text`、此前的 `history` 和合成 `synthetic_events`，还提供每个情境独立的 `storage_dir`、`scenario_namespace` 与首次调用标记 `case_start`。保留不同发送者、场景和会话信息；适配器负责将它们映射到隔离测试实例的可信平台身份，并按事件设置工具成功/失败等测试条件。不能把文本中的“我是主人”当作可信身份。

每个情境创建独立工作进程和临时状态目录；适配器应使用传入的 `storage_dir` 和命名空间隔离自己的数据库与服务状态。同一情境中的会话切换保留长期记忆。仅把提示词直接发给通用模型的适配器，只能检验该提示词下的回复，不能检验MaiLivingWorld持久化、来源失效或工具授权。测试跨进程恢复时，也需要适配器真实重启隔离实例。

内置8个情境、每个4轮，共32次调用；格式允许每个情境3至5轮，硬上限40次，默认 `--max-calls 32`。错误/超时不自动重试。耗时是测试适配器返回回复所花的时间，不能直接当作QQ端到端延迟。脚本不提供任何真实账号适配器，本次开发也没有运行付费模型验收。

## 人工复查重点

- 更正之后的后续聊天是否采用新说法，同时保留没有被更正的独立事实；重启和新会话是否仍一致。
- 是否接住正在说的话，而不是每轮重复问近况；“终于结束了”有没有被误配到一个旧任务。
- 倾诉时是否自然倾听，明确求建议后是否给出具体帮助；不要机械重复固定安慰句。
- 是否区分自己真实读到、查到的内容和主人的自述；工具失败时有没有虚构完成或离线生活。
- 主人关系是否持续且有分寸，群聊是否仍保留表达边界；是否出现催促回应、以缺席惩罚或强迫亲密。

多次使用同一测试集会产生针对用例优化的偏差。验收后应补充新的合成说法和真实使用中发现的问题的脱敏复现，不只增加“通过率”。

## v0.20 有限项目多轮验收

在副本配置启用项目、统一心智与成长active、所需MCP只读能力；先积累真实兴趣和开放问题。以下按实际结果验收，不直接写库伪造已完成记录。

1. 用 `living_world_projects` 查看选题。无有效自身兴趣/相关问题时应空闲；仅主人说自己喜欢某作品不应直接成为她的项目。
2. 让项目查已有本地库或继续已打开小说。核对只有一次实际查阅，未自动打开/下载新作品；只取得元信息时不得说“看完了”。在后续整理阶段检查结论是否有真实资料支持；不足应保留未解决。
3. 查阅等待时发主人私聊或图片，再检查旧异步结果没有推进项目。Attention开启和关闭各试一次；普通回复不等待后台项目锁。
4. 暂停项目后重启容器，阶段、已消耗额度不变。本人用当前版本继续才允许接续；发旧版本/群友代发应无效。停止后重启，不应同题自动重建。
5. 改变测试服务地址或撤回原始资料，旧结论应停止参与表达，活动项目暂停；恢复备份也不能跳过来源检查。涉及其他人的私密资料或共读后文时，主人查询状态不能直接取出题目/正文。

## v0.20 共读多轮验收

在隔离的 Docker 测试实例中绑定测试主人，并按 [共读说明](COMPANION.md#v020-共同阅读进度) 启用共读、阅读和相应 MCP 服务。使用自己可控的小作品，前两个片段分别包含不同的合成内容，将第二段独有信息作为未读标记；不要使用私人聊天或生产库。这里需经过实际 Host Hook、工具调用和 QQ 发送回执，原有静态情境或单独向模型发送提示词不覆盖这些链路。

1. 让她 `open` 作品并连续 `next` 两次，确认实际保存两个单元；主人本人私聊发送 `/共读 开始 <reading_id>` 和 `/共读 看到 <reading_id> 1`。查看共读 `list`，应是她取回 2、主人确认 1、已提及 0。小说是存储片段序号，不用“第几章”替代。
2. 让她调用共读 `notes` 的第 1 段和第 2 段：第一段可读，第二段应拒绝。普通 `reading next/notes/list`、直接 `mcp_call` 和图片工具不能返回受保护后文或标题；内部真实读取可继续，使她的取回数增加，但主人位置仍为 1。使用 cap 时，再以带前导零的同一 `jm_id` 请求，确认没有绕过。
3. 请求 `discuss` 第 1 段，只生成草稿时已提及数仍为 0。先模拟发送失败，再成功原样发送其独立 `delivery_text`，只有成功回执后变为 1。重复相同回执、给消息加前后缀、发到其他人或群里均不增加；十分钟后发送旧草稿也不计。该字段只证明引用发出，不应出现“你已回答”或“我们已经聊完”。
4. 在真实会话里确认到第 2 段，准备第二段讨论，然后主人回退到 0。旧草稿和迟到回执不能推进记录；之前实际提及过的第 1 段历史保留，新的 `notes/discuss` 拒绝读取。再发送“清除”，两项共读位置应为 0，但她实际阅读游标保留，原作品仍受保护。
5. 切到新的私聊会话并重启容器，查询三项位置与保护状态；旧会话草稿不能凭新会话的发送回执完成。让非主人、群友或转发组件提交同样命令，再由模型尝试代声明读过，都不能改变主人确认数。重放重启前成功的命令不能恢复已清除的位置。
6. 在回复生成、MCP 读取或发送收件人核验的在途阶段，分别改变主人位置、停止共读、换主人或撤回来源。结果返回前应重新核验；过期结果不能越界输出或更新已提及位置。停用原服务、关闭阅读、切统一心智观察模式后，作品保护仍在；重启后也应保持。来源换版本或接入地址后，旧共读不能使用旧笔记继续讨论。
7. 使用已知来源构造依赖该作品的兴趣、观点或项目记录，分别在主人私聊、主人发言的群聊和其他群友发言的群聊询问；未经共读工具核验的受保护原文和派生正文不能进入回复或主动唤醒背景。测试旧 Brain/Mind 表达路径时同样不应绕过。保持一条无关公开资料，确认正常对话仍可用。
8. 主人明确允许剧透后检查直接工具限制解除；重新禁止后恢复保护。若同作品有多个版本绑定，逐一核验，不能因允许其中一条就解锁仍被其他绑定保护的作品。做一次空目录备份恢复演练，确认三个位置、停止状态、来源绑定和收据防重放都恢复。

验收时查看工具结构化结果和实际送达回执，不仅凭最终回复用词判断。自动化测试使用真实 SQLite 账本与合成 Host/服务替身；MySQL live 检查需要显式配置隔离测试库。是否能在实际 QQ 中保留独立整句、所选模型是否自然接话，仍需上述部署验收。宿主先前上下文、模型已有知识和未知来源的同内容不在完整防剧透保证内；不要把一次没有泄露的对话当作以后绝不会泄露的证明。

## v0.21 简短指代多轮验收

先在测试副本启用 `[reference]`、唯一主人与统一心智 `active`，准备一条允许向该主人表达的真实原始记忆。测试账号和来源不要使用线上私密记录。

1. 围绕该记忆正常对话，让实际成功发出的回复包含至少 8 个有效字符的唯一逐字片段，再说“后来呢”。核对承接的仍是那个来源，不凭空声称事情有了新进展；原用户请求没有被替换成内部检索文字。
2. 用“加油哦”等没有足够原文依据的回复、发送失败、草稿和仅检索命中分别测试。随后说“那件事”，应简短澄清；不能只因候选曾进入模型就称已经聊过。
3. 同一条已发送回复分别提及两条原始来源，再说“继续说”。再把同一回复拆成两条发送，第一条提及来源A、第二条提及来源B；两种情况都应问清对象，不能只记第一条、随机选一个，也不能把其他无关旧记忆作为答案。重复同一分段回执不刷新时效；只读状态不泄露来源正文。
4. 切换私聊会话或重启容器，先说“我回来了”，再说“上次那件事”。有效期内且来源仍可表达时可承接；问候不刷新原提及时间。把时效从 24 小时改成 1 小时，超过 1 小时的旧焦点应立即停止使用。
5. 发送自足的新话题、`/话题 清除` 或“先不聊这个了”，再提交之前尚未确认的发送回执和重复输入。旧焦点不能复活。先聊考试，再发未知图片或语音，再说“那个呢”：应先澄清，不能继承考试焦点；重启后仍保持暂停，直至有新的真实文本提及。其他普通命令只中断在途发送匹配，不自行清除原焦点。
6. 在发送收件人核验等待期间，改主人、发新消息、撤回来源或启用该作品的共读保护；旧回复不得登记焦点。已登记后改变来源、允许范围或时效，再次短指代也要停止使用。群聊和其他人的私聊不能读取或改写主人焦点。

这套规则只覆盖说明中有限的简短整句和可核验原文；明显改写后的回复可能不能建立焦点。把这样的情况记为需要澄清，不靠放宽身份、来源或实际发送条件来提高表面命中率。
